Prepared November 15, 2026. Working repository name `agentic-runtime`. First implementation `v0.1.0` (experimental).

The sections below describe the intended scope, including research criteria still pending. Specific differences: usage reports token counters but no dollar estimate; operation records retain attempt counts and transition events, not separate timestamped objects for every attempt; context is refreshed before decisions and actions enforce their own state preconditions; task updates serialize in SQLite transactions and execution uses file locks rather than distributed leases; redaction is configurable but raw arguments and replies may contain sensitive data. Keep secrets in dependencies and review the persistence contract.

## Product goal

Let a developer add an agent to an existing application using application functions, explicit user context, and a persistent task lifecycle. The runtime carries the task through model calls, tool execution, user questions, approvals, recovery, and result checks.

The initial user is a Python backend developer adding an agent to a product with existing users, business logic, and a database.

The differentiation hypothesis is that a small, coherent API substantially reduces custom coordination code while retaining understandable failure behavior. We will measure this against a carefully implemented existing-framework baseline.

The host supplies authentication, tenant membership, business permissions, and deployment supervision. SQLite is used for runtime state. The host application's domain database remains application-owned. Tools execute with the worker's operating-system permissions, so application tools are trusted code.

## Eight components

### 1. Agent execution

The model selects from registered actions and receives validated results. The runtime executes one action at a time and continues until verification, a user wait, a blocker, cancellation, failure, or a resource limit.

The runtime stores a concise task objective, structured progress, messages, and tool outcomes. A model may maintain a brief plan as task data. The initial loop uses a straightforward tool-calling strategy.

Developer controls include maximum model calls, maximum tool calls, per-call timeouts, active execution deadline, and output size limits. Counters survive restart. Waiting for a human has a separately configurable expiry. Model usage is recorded, and dollar estimates are labeled estimates.

### 2. Typed actions

An Action contains its name, input and result schemas, implementation, and declared execution behavior. Execution behavior includes whether the action reads or writes, whether approval is required, and how retries are supported.

Every dispatched operation has a persisted operation ID, input digest, attempt history, and outcome. Action code receives the operation ID for provider idempotency or application deduplication.

Read actions can retry transient failures within a limit. Write actions require a declared safe retry or reconciliation mechanism. A changed payload is a different operation and invalidates approval for the prior payload.

The interface supports an optional reconciliation callback that checks the external service for an operation's outcome. It returns applied, not applied, or unknown, plus any external record reference. A not-applied result must be authoritative enough to exclude a delayed commit before retry is allowed.

### 3. Application context and authorization

Each task belongs to a host-supplied workspace and initiating user. Dependencies provide scoped application clients. A context callback loads current business state before decisions or actions that require it.

An authorization callback runs before every action dispatch and again after an approval wait. Host-defined preconditions check versions or business rules, and write adapters use conditional updates when the external service supports them.

The runtime retains a bounded working history and stores large tool outputs as artifact references. Required pending-operation and approval records remain available through context reduction. For the initial release, deterministic truncation and retrieval are sufficient. Cross-task learned memory is a later capability.

### 4. Persistent task lifecycle

Persist tasks, model messages, operation records, approval and input requests, evidence, resource counters, and ordered events.

The task states are queued, running, waiting_input, waiting_approval, verifying, succeeded, blocked, failed, and cancelled. Cancellation is first recorded as a durable request and checked before each dispatch and before accepting completion.

| Situation | Transition |
| --- | --- |
| Submit a task | queued |
| Worker claims a task | queued to running |
| Agent asks a question | running to waiting_input |
| An action requires approval | running to waiting_approval |
| Authorized input or approval arrives | waiting state to queued |
| Agent proposes a result | running to verifying |
| Required checks pass | verifying to succeeded |
| A failed check allows another attempt within budget | verifying to running |
| An unresolved external outcome needs attention | running to blocked |
| A terminal execution error or exhausted budget occurs | running or verifying to failed |
| Cancellation reaches a safe boundary | active or waiting state to cancelled |

Operation outcome is recorded separately from task state. A cancelled task can contain an applied or unknown operation.

A SQLite transaction atomically updates task state and appends the corresponding event. Claims use version checks and an exclusive worker ownership mechanism. Startup recovery distinguishes completed operations, undispatched operations, and operations whose dispatch may have happened. A local claim alone cannot prevent an external duplicate, so external writes still require the action's declared recovery contract.

### 5. Human input and approvals

The agent can request structured input and wait durably. Approval requests show the exact action, target, and arguments. Approval is bound to the task, operation ID, input digest, and the application actor authorized to approve it.

Duplicate replies are idempotent. Stale approvals and replies for an inactive task are rejected with an actionable response. Rejection returns a recorded decision to the runtime so the task can stop or find an allowed alternative.

V1 accepts additional user input at explicit waiting points and supports cancellation at any task state. Mid-action goal revision will be designed after the basic lifecycle and recovery contract are proven.

### 6. Recovery and bounded execution

When a model request fails, apply bounded retry with backoff. When a read action fails, use its declared retry policy. When a write times out or the worker stops after dispatch, reconcile it before choosing a retry.

| Recorded operation state | Recovery behavior |
| --- | --- |
| Completed with persisted result | Reuse the recorded result |
| Intent persisted, dispatch known not to have started | Dispatch under the original operation ID |
| Dispatch may have occurred | Reconcile or use provider-backed idempotency |
| Outcome remains unknown | Block the task and preserve the evidence |

Adapters must document their assumptions about idempotency-key retention, eventual consistency, and external status queries. The runtime's guarantees are bounded by those capabilities.

Cancellation prevents further dispatch after the runtime processes the cancellation request. Already dispatched operations are tracked to a known or explicitly unknown outcome. Their effects remain visible in the result record.

### 7. Result checks and evidence

The application registers completion checks. The runtime runs them after a proposed result and ties the check results to the relevant task and operation records. For mutable external state, checks include the observation time and available record version.

A result contains the output, passed and failed checks, actions performed, artifact and external-record references, unresolved outcomes, usage, and remaining review items.

A successful task means the configured completion checks passed. Check coverage is explicit. Application checks should inspect actual state where possible. Subjective assessment can be recorded separately with its method and uncertainty.

Check failures become bounded repair feedback. Missing required checks or unresolved required outcomes prevent success. Evidence writers and completion status are runtime-owned.

### 8. Application API and progress events

The Python surface should cover task creation, status, input requests, approval decisions, cancellation, result retrieval, and event subscription.

The optional FastAPI integration exposes these operations to the host application. Each endpoint requires host-provided identity and ownership checks. Progress events carry durable monotonic IDs, allowing clients to reconnect after the last seen event.

Human-facing events describe actions, waits, check results, and outcomes. The runtime offers configurable redaction and artifact retention. Application secrets remain in dependency injection and are excluded from persisted context and ordinary logs.

Examples and tests stay outside the core package. Additional abstraction layers require a concrete caller or a demonstrated implementation need.

## Reference application

Build a support assistant that reads a ticket and related records, investigates the issue, updates internal notes, drafts a response, obtains approval to send, sends it through a controlled delivery service, and verifies the delivery record and ticket state.

The application owns ticket and user data. The runtime owns task and operation state. A deliberately controllable service can apply a send and then drop the response, making ambiguous outcomes reproducible. A dry-run path runs without a model key using the scripted adapter. A live-model path exercises the same task lifecycle.

The demonstration must show completion, rejection, additional user input, restart during a wait, a crash around a write, cancellation, and an unresolved external outcome. The UI displays what happened and which decision is needed next.

Before release, add a second small project-management example that creates release tasks and verifies them. Reuse the public API and record any application-specific coordination still required.

## Acceptance criteria

| Scenario | Required evidence |
| --- | --- |
| Happy path | Application records and configured checks confirm the requested outcome |
| Restart during user wait | Same task and pending request survive, and a valid reply resumes the task |
| Completed tool step followed by crash | Persisted result is reused |
| External write commits and response is lost | Provider idempotency or reconciliation resolves the original operation without an additional effect |
| External outcome cannot be determined | Task becomes blocked with an unknown operation outcome |
| Duplicate approval or input submission | One state transition and at most one logical dispatch |
| Action arguments change after approval | Prior approval is rejected for the new payload |
| Permission changes while task waits | Dispatch is refused when current authorization fails |
| Cancellation while tool runs | Later operations are suppressed and in-flight outcomes remain recorded |
| Two consumers race to claim a task | One valid owner advances the task under the supported single-host model |
| Model or tool limit is exhausted | Task stops and preserves usage and partial effects |
| Browser reconnects | Events continue from the last event ID |
| Required completion check fails | Task repairs within budget or returns a non-success result |
| Another workspace requests task access | Host identity checks reject access in the reference integration |
| Large history reaches the context budget | Pending decisions and operation evidence remain usable |

Deterministic tests exercise crash boundaries and external service behavior. Live-model runs evaluate task completion and recovery behavior across repeated runs. Both result sets are reported with their assumptions and configuration.

## Comparison experiment

Implement the same support workflow using a current LangGraph-based stack with documented idiomatic patterns. Pin versions and give both implementations the same model, tools, scenarios, and resource limits.

Measure application-specific coordination code, setup steps, implementation effort, custom recovery code, task success, false success, duplicate external effects, interventions, latency, and token cost. Publish failures and setup limitations alongside successes. Keep a held-out set of task variations so the demonstration's fixed path is insufficient to pass.

A second developer should be able to build the project-management example from the public documentation. Record where they need undocumented help. An advantage must survive both the behavior comparison and the developer experience exercise.

## Implementation milestones

1. Reference workflow and baseline. Define observable outcomes, model and service interfaces, and the test scenarios. Implement the baseline and record its coordination code.
2. First vertical slice. Implement typed actions, the agent loop, SQLite task records, and one complete task using the scripted and real model adapters.
3. Durable interaction. Add user questions, exact-action approval, worker recovery, and ownership checks.
4. Recovery and checks. Add operation reconciliation, cancellation, resource limits, completion checks, and the failure test matrix.
5. Application integration. Add the FastAPI router, reconnectable events, and support UI. Exercise the second application and simplify the public API.
6. Release validation. Run the comparison, publish measured results, and release v0.1.0 with installation instructions and working examples.

## Subsequent capabilities

Later releases can add PostgreSQL and multi-host workers, additional model providers, MCP integration, richer context compaction and cross-task memory, live task revision, delegated agents, and deployment integrations. Each addition needs a concrete application requirement and a testable contract.

## Decisions to revisit after the first application

Keep the working name until repository and package naming are confirmed. Validate provider coverage with initial users. Reconsider the storage backend when deployment demands multiple hosts. Revise API names after both examples compile and pass the acceptance scenarios. Keep the benchmark outcome open until measured.
